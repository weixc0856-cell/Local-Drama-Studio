# 设计决策记录（ADR）

每条记录：背景 → 决策 → 后果。后续若推翻，新增一条并注明取代关系，不直接改写历史。

---

## ADR-001 ComfyUI 只做生成引擎

**背景**：ComfyUI 有节点、队列和界面，容易把业务逻辑也塞进去；但它的状态不可查询、不可恢复，节点升级会破坏流程。

**决策**：ComfyUI 只接受 API 格式工作流、执行生成、返回文件。剧本、分镜、人物资产、重试、质量门、剪辑全部在 Python 调度层。

**后果**：

- 生成失败可以只重跑单镜头。
- 工作流变更不影响业务状态。
- 需要自己实现 HTTP/WebSocket 客户端与状态库（R3）。

---

## ADR-002 调度与生成使用两个独立虚拟环境

**背景**：ComfyUI 依赖特定 PyTorch/XPU 版本；业务依赖 httpx/typer 等轻量库。混在一个环境里，升级 ComfyUI 会破坏调度层，反之亦然。

**决策**：

- 根 `.venv`：Python 3.12，禁止安装 torch。
- `runtime/ComfyUI/.venv`：Python 3.12，PyTorch XPU + ComfyUI + GGUF 节点。

**后果**：

- 磁盘多一份 Python 环境，但互不污染。
- 所有跨环境调用通过 HTTP/子进程，不能直接 import。
- `doctor` 必须分别检查两个环境。

---

## ADR-003 模型权重统一存放 `models`，不复制

**背景**：多个 AI 项目重复下载十 GB 级权重既浪费磁盘，也会造成版本漂移。

**决策**：唯一模型仓库为 `models`；ComfyUI 通过 `extra_model_paths.yaml` 引用。新文件放子目录，顶层 GGUF 保持原位。

**后果**：

- 节省磁盘、版本单一。
- 必须遵守 `start_server.bat` 只扫描顶层的约束。
- 工作流里不能写死 ComfyUI 本地的 `models/` 路径。

## ADR-004 项目 LLM 使用 8081，流水线优先 CPU-only（已被 ADR-013 取代）

**背景**：2026-11-02 实测 8080 被另一个需要 API Key 的实例占用；同时 8GB 显存无法让 LLM 与 Wan 共存。

**决策**：

- 项目自己的 llama.cpp 实例监听 **8081**。
- 长流水线默认以 `-ngl 0`（CPU-only）运行剧本/分镜阶段；需要 GPU 加速时手动切换，并在跑图前停止。

**后果**：

- 避免端口冲突与显存争抢。
- 剧本阶段变慢，但 64GB 内存与 24 线程足以处理几千 token 的结构化输出。
- 编排层必须检查 8081 是否在线，且不得依赖 8080。

**2026-11-03 更新**：默认实例已按本决策以 `-ngl 0` 运行，模型 `Qwen3-30B-A3B-Instruct-2507`，`-c 65536`（64K 上下文，已验证可用），不占显存。同日改为单端口 8080，见 ADR-013。

## ADR-005 以镜头为最小任务单元，SQLite 存状态

**背景**：整段生成失败代价高；引入 Redis/消息队列对单机项目过重。

**决策**：每个镜头独立状态机与任务记录；状态存项目内 `state.db`（SQLite WAL）；并发固定为 1。

**2026-11-03 现状更新**：项目级 `state.db` 未实现。当前实现使用 `projects/workspace.db` 保存项目/期数/风格/任务，生产状态由文件派生；本 ADR 的“每镜头状态机”仍是目标，不是现状。

**后果**：

- 断电/崩溃后可断点续跑。
- 无需额外服务。
- 状态迁移必须显式记录，不能靠文件是否存在猜测。

## ADR-006 只保留三个人工控制点

**背景**：全自动会产出"技术成功但内容不可用"的成片；全人工则失去自动化意义。

**决策**：H1 人物定妆、H2 首帧批量确认、H3 最终成片验收。其余环节自动。

**后果**：

- 一致性风险在视频生成前被拦截。
- 需要简单的 review 文件和 CLI 交互（R5/R7）。
- 不追求无人值守出片。

---

## ADR-007 先生成全部首帧，再批量生成视频

**背景**：视频生成是最贵、最慢的一步。人物服装/场景错误如果在视频阶段才发现，返工成本最高。

**决策**：S3 生成全部 keyframe → H2 审核 → S4 批量 I2V。

**后果**：

- 提前暴露一致性问题。
- 首帧阶段可以低成本重摇。
- 流水线多一个同步点。

---

## ADR-008 数据契约优先，LLM 输出必须过 Pydantic

**背景**：本地 LLM 容易输出"文学性描述"或多余字段，下游无法稳定消费。

**决策**：`Storyboard` / `Shot` / `Character` 严格校验（`extra="forbid"`）；失败时把校验错误回喂，最多修复 2 次；仍失败则阶段失败。

**后果**：

- 下游永远拿到结构化数据。
- 需要维护提示词与 Schema 同步。
- 修复循环必须限次，不能无限调用。

---

## ADR-009 剪辑只用 FFmpeg

**背景**：MoviePy/Remotion 引入 Python 转码层与额外依赖，且难以精确控制音频/字幕。

**决策**：归一化、拼接、混音、字幕、转码全部用 FFmpeg 子进程；参数以 argv 列表传递。

**后果**：

- 行为可复现、命令可记录。
- 需要自己写少量滤镜图拼装代码。
- 不引入 Node/Python 视频框架。

---

## ADR-010 技术质量与内容质量分开记录

**背景**：文件能打开、时长正确，不代表镜头可用。

**决策**：`review.json` 分别记录 `technical`（自动）与 `human`（人工）结论；只有两者都通过才进入 `COMPLETED`。

**后果**：

- 状态机多一个门槛。
- 报告能区分"生成失败"与"生成成功但不想用"。

---

## ADR-011 首阶段不承诺人物一致性与口型同步

**背景**：8GB 本地模型 + 无专门换脸/口型模型，跨镜头像素级一致性不现实。

**决策**：一致性目标是"可辨认、服装与气质连续"；镜头语言优先使用旁白、背影、侧脸、特写、反打，避免把口型同步作为硬指标。

**后果**：

- 剧本与分镜阶段需要约束镜头类型。
- 后续若要提升，再单独评估 IPAdapter / 换脸 / 口型模型，不提前引入。

---

## ADR-012 先 CLI，后界面

**背景**：核心风险在生成链路与状态管理，不在 UI。

**决策**：R0-R7 只做 Typer CLI；网页后台不作为短期目标。

**后果**：

- 开发聚焦在流水线与验收。
- 需要设计清晰的命令与 JSON 输出，便于以后接 UI。

## ADR-013 本地 LLM 只用 8080 一个端口，定时任务让路

**背景**：ADR-004 的"项目用 8081、定时任务用 8080"形成了两个本地 LLM 端口。第二个端口要求所有调用方额外记忆，容易出现请求被错误实例接走（Windows 允许 `127.0.0.1` 重复绑定），也让下游项目多一份配置。2026-11-03 决定收回到单端口。

**决策**：

- 本地 LLM 统一使用 **8080**，不再使用 8081。
- 项目运行期间由项目的 llama.cpp 实例占用 8080（默认 CPU-only、64K）。
- 定时任务（`OpportunityRadarDaily`）启动自己的 llama-server 前先检测 8080：若被占用或仍有未完成请求，按间隔等待；等项目实例释放后再启动；任务结束后停止自己启动的实例，把端口还给项目。
- 不为某个定时任务更改项目端口。

**后果**：

- 所有调用方只记一个端点，不再有 401 / 错误实例的端口歧义。
- 定时任务可能被推迟（受最长等待上限约束），日志必须记录等待原因与时长。
- 实例生命周期要明确：谁启动，谁结束时停止。

## ADR-014 建立本地生产工作台，取代 ADR-012「只做 CLI」

**背景**：ADR-012 把网页后台排除在短期目标之外，理由是核心风险在生成链路与状态管理，不在 UI。实际执行到 R3-D 后，生产状态分散在 `experiments/`、`literary_intelligence/runs/`、`logs/` 与多份 JSON 中；每次查看进度、失败原因和产物都需要手工翻目录，已经影响判断效率。新的需求是“让前端成为统一操作入口”，但前提是不得伪造状态、不得绕过服务生命周期。

**决策**：

- 建立本地单用户工作台：FastAPI 后端 + 无构建步骤的 ES Modules 前端，运行在根 `.venv`，不新增 node 环境。
- 前端**只读派生**：项目/期数/风格/任务记录存 `projects/workspace.db`；所有生产状态从真实文件实时派生。
- 前端**受限执行**：只有任务注册表中的固定入口可被触发，参数严格校验，单飞锁，遵循 8080/8188/50000 与 GPU 单租户规范。
- 未实现的能力在 UI 中显式标注 `NOT_RUN` / `BLOCKED`，不以占位数据冒充。

**后果**：

- ADR-012 中“网页后台不作为短期目标”一条被本 ADR 取代；CLI 仍是正式入口，`drama serve` 与其并存。
- 新增依赖 fastapi / uvicorn（MIT / BSD-3-Clause），不引入 torch、数据库服务或前端打包链。
- 工作台不改变 R3/S3 已验证链路；重建任务必须写入新目录，禁止覆盖 `experiments/r3b/renders`。
- 若后续要做内容编辑、内容包 Adapter、版本化，必须另立阶段并先补数据契约。

## ADR-015 视觉方向收敛为双核心风格

**背景**：R1 建立的视觉基线偏水墨/自然纪实，R3 样片也只验证了这一方向。若继续按“工笔、敦煌、国漫、写实”并列扩展，模型、算力与工程资源会被摊薄，且没有任何一种风格有完整的生成与动画验证。工作区已有可复用的风格实体、期数快照和提示词拼接链路，不需要第二套风格系统。

**决策**：

- 产品只建设两种核心视觉配置：`court_green_fine_line`（宋代院体青绿工笔）与 `ink_wash`（东方写意水墨）。
- 两种风格共享同一套生产系统；差异通过 `config/styles.yaml` 的配置项表达，不在代码中按风格分支。
- 规范落在 `docs/VISUAL_STYLE_SPEC.md`；配置由 `src/drama_studio/style_presets.py` 严格校验，并可导出为工作台 `styles` 实体。
- 预设不自动写入 `projects/workspace.db`；数据库只存用户创建的事实。
- 动画以确定性合成为主（长卷横移、水墨遮罩、墨迹渗染、纸纹、线描显现），Wan 仅做局部动态补充。
- 不新增风格模型、LoRA、插件系统或动画框架。

**后果**：

- 风格数量不再作为产品发展方向；新增第三种风格必须另立阶段并重新说明资源。
- S1（规范与配置）为 `PASS_STATIC`；两种风格的真实生成、动画与完整链路仍为 `NOT_RUN`，不得写成已验证。
- 历史 R1/R3 视觉资产继续作为证据保留，但不自动等同于任一核心风格的验证结果。
- `docs/CONTENT_SPEC.md` 的 R1 色板被明确为 `ink_wash` 的近似方向；冲突时以 `VISUAL_STYLE_SPEC.md` 为准。

## ADR-016 图像线切换到 FLUX.3，旧风格体系退役并重设计

**背景**：2026-11-06 的 POC 在当前机器上跑通了 FLUX.3 Image Klein（GGUF Q4_K_M + Qwen3-VL-4B 文本编码器 + XPU，576×1024 约 2.5 分钟/张，5/5 成功）。同时确认了三件事：

- 官方 9B 提示词放大器在本机不可用：XPU 在 `model_prefetch` 路径稳定崩溃，CPU 上 fp16/bf16 均为 51–66 秒/token。
- 本地 `Qwen3-30B-A3B` 使用官方 `t2i` 系统提示词可以替代放大器：单条 caption 55–97 秒，端到端 3.5–4 分钟/张，画面内题跋消失。
- FLUX.3 的失败模式与 FLUX.2 时代为 FLUX.2 设计的提示词体系直接冲突：750 字指令堆叠、十六进制色值、只存在于负向提示词里的约束（CFG 1.0 下从未生效）、以及提示词内部的留白/内容矛盾。

**决策**：

1. FLUX.3 Image Klein 成为唯一图像生成线；FLUX.2 Klein 保留为过渡期回退，不再作为默认。
2. 提示词链路改为「官方 `t2i` 系统提示 + 本地 Qwen 生成英文 caption」，不依赖 9B 放大器，不引入新的大模型。
3. 现有 `config/styles.yaml` 的四种风格定义与 FLUX.2 工作流在过渡期后下线，风格重新设计。
4. 新风格契约面向 FLUX.3：自然语言描述、无十六进制色值进入 caption、留白用单块正向描述、比例与画布术语不进入 caption。
5. 度量口径改为纸面相对留白，色度阈值从新风格规范推导，不再以 FLUX.2 输出作为唯一基线。
6. 历史证据保留：R1/R3 视觉资产、11-04 的 A/B 批准记录、`production_baselines`、旧模型文件与旧工作流归档，不删除。

**后果**：

- `config/styles.yaml` 不是纯视觉文件：`motion/`（摄像机、缓动、局部微动）、`style_consistency.py`、`static_quality.py` 的检查清单、`aesthetics.py` 的六维设计都依赖它。删除前必须先把 motion policy 拆出或随新风格重建，否则这几条链路会同时断。
- `production_baselines` 与 `docs/PIPELINE_AB_VALIDATION.md` 记录的是旧基线的批准事实，只能归档，不能当作新风格的验证。
- 新风格需要新的静态检查清单与基线，不能沿用 `CHECKLISTS` 里的旧条目。
- 过渡期内保持双轨：新线验收通过前，FLUX.2 仍可回退。
- 旧风格的质量状态保持原样（`PASS_STATIC` / `PARTIAL`），不得因为退役而改写成已验证。

## ADR-017 VoxCPM2 作为唯一语音生成线

**背景**：CosyVoice2-0.5B 与 SFT 预置音色已退役（2026-11-06）；VoxCPM2 在盲听对照中 7/7 优于旧模型，48 kHz 输出，CPU 推理不占显存。

**决策**：

- 语音生成只走 VoxCPM2，服务端口统一 **50000**，调用方通过 HTTP 而非内部 Python 函数。
- 参考音与逐字文本由调用方提供；服务不做业务判断。
- 情绪/语速等控制字段属于本系统适配层，映射到模型支持的文本指令与推理参数，不假设模型原生字段。

**后果**：`voice/tts.py` 的运行时校验固定为 VoxCPM2；SFT 路径直接报错；ASR QA 的 Whisper 安装在 VoxCPM2 运行时内。

## ADR-018 Wan 作为本地视频生成线，按镜头生成

**背景**：Wan2.2 TI2V 5B 是唯一在 A750 上实测可用的视频模型；原生首尾帧控制主要在 14B 上验证，5B 不能假设可用。

**决策**：

- Wan 只承担镜头级生成，不承担叙事、分镜或跨镜头连续性。
- 每个镜头有明确的运动主体：环境运动 / 摄影机运动 / 主体运动，三者不得同时堆叠。
- 连续性优先靠关键帧继承与剪辑规则实现；模型级首末帧锁定列入 Phase 2 候选，不进入当前依赖。

**后果**：分镜必须给出运动主次；只有数字放大的镜头不得标记为电影级运镜。

## ADR-019 引入 Script-to-Film 制作架构

**背景**：现有链路「出图 → 加运动 → 拼接」缺少影视制作层，导致镜头之间没有空间与叙事关系。

**决策**：

- 在图像生成与视频生成之间增加独立的制作层 `src/drama_studio/film/`。
- 剧本、分镜、视觉圣经、声音、关键帧、镜头与剪辑时间轴共享同一份项目数据；`storyboard.json` 是镜头的唯一事实源。
- 所有模块通过严格 Schema 校验；生成任务只读取项目数据，不各自维护状态。
- 制作层不直接调用 ComfyUI；生成仍由 `production.py` 与任务系统执行。

**后果**：新增 `project.json` / `screenplay.json` / `narration.json` / `visual_bible.yaml` / `storyboard.json` / `timeline.json` 契约；旧 `production_script.json` 保留为生成输入，由分镜派生。

## ADR-020 以镜头连续性与影视语言作为质量标准

**背景**：过去用图片数量、转场数量与单帧指标衡量进度，无法反映成片是否像电影。

**决策**：

- 质量判定以镜头连续性、摄影语言、叙事对应、声音与剪辑为准；图片数量与转场数量不作为生产指标。
- 五条硬规则：结构变形、跨镜漂移、旁白错位、无透视的假运镜、字幕/诗词/音频错误，任一出现不得交付。
- 自动指标只做筛选；成片必须有人工审片记录，状态才可标记通过。

**后果**：`PRD-STYLE-*` 与动画要求的验收方式随之调整；旧的单帧 A/B 结论不能替代成片验收。

## ADR-021 引入 Visual Style Engine（12 套 Style Pack）

**背景**：产品目标从单一国风短片扩展为多风格影视生产。若风格只是提示词集合，FLUX 与 Wan 会各自漂移：水墨变写实云雾、工笔丢线描、浮世绘出现写实景深。

**决策**：

- 建立 `config/style_packs/<group>/<name>/` 的 Style Pack 体系，12 种风格全部纳入：retro 4、oriental 3、artistic 5。
- 每个 Pack 独立版本化，包含风格身份、图像规范、视频规范、摄影、运动、光线、色彩、材质、禁止项与参考板要求。
- 风格必须同时约束 FLUX 与 Wan；禁止项以正向锚点表达，十六进制色值只用于校验，不进入提示词。
- 项目只绑定一个主风格并冻结；混合/渐变需显式声明，默认关闭。
- 新增风格只增加 Pack 并注册，不修改核心引擎。
